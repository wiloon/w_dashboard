# ADR-010: 仓库状态刷新——并发采集 + 逐行增量更新

## Status

Accepted（细化 SDD §8 的刷新策略；不改变 ADR-003 的采集方式与 §7 的派生规则）

## Context

**问题**：两端最初的实现都是"整批刷新"：点刷新按钮（或定时/启动触发）后，后台把配置里的**所有**仓库**串行**采集完，再一次性把整个列表推给 UI。

- app-linux：一个后台线程 `map(collect_repo)` 收成 `Vec<RepoStatus>`，通过 channel 一次性发给 UI。
- app-macos：一个 `Task.detached` 里 `repos.map { collectRepo(...) }`，回主线程整体替换 `repoStatuses`。

**痛点**：单个仓库的采集成本不低——`git status` 之外，开启 `fetch_remote` 时还有一次 `git fetch`（走网络、可能超时，上限是 `command_timeout_secs`）。于是：

- 用户要等**所有**仓库都采完才看到**任何**结果；仓库越多、网络越慢，白屏等待越久。
- 一个慢仓库（远端不可达、卡到超时）会拖住其余所有已经采好的仓库，与"单项失败不拖垮整体"（SDD §2 原则）的精神不符——数据虽然已经有了，却被压在最后统一呈现。
- 总耗时是所有仓库耗时之**和**，纯粹由串行造成。

**约束（不变）**：
- 仍是只读采集，仍通过子进程调 git（ADR-003），§7.1/§7.2 的解析与派生规则一个字不改。
- 采集层与 UI 分层不变：异步/线程调度归各端 UI 层自己（SDD §8 标题即"刷新策略（UI 负责）"）。
- 两端不共享代码（ADR-002），一致性仍由 `docs/test-vectors/` 保证；本变更不触及任何向量。

## Options Considered

| 方案 | Pros | Cons | 复杂度 | 何时合适 |
|------|------|------|--------|----------|
| A. 维持整批串行刷新 | 实现最简单；UI 只有"全旧"和"全新"两个状态，无中间态 | 首个结果的等待时间 = 全部仓库耗时之和；一个慢仓库拖垮整屏 | 低 | 仓库数很少（1–2 个）且都在本地、不 fetch |
| B. 串行采集 + 逐行更新 | 用户很快看到第一行；改动小 | 总耗时不变，仍是求和；最后一个仓库该等多久还是多久 | 低 | 只想解决"首屏等待"，不在意总时长 |
| C. **并发采集（有上限）+ 逐行更新** | 首行秒出；总耗时约降至 1/N（N=并发度）；慢仓库只拖住自己那一行 | 需要处理：行序稳定、代际（新旧刷新叠加）、并发上限、UI 中间态文案 | 中 | 仓库数从几个到几十个，且可能开 `fetch_remote` |
| D. 无上限并发（一仓库一线程） | 总耗时最短 | 仓库多时线程/进程数失控，同时 N 个 `git fetch` 打爆网络与磁盘 IO；对远端也不礼貌 | 中 | 仓库数固定且很少 |

## Decision

**选择方案 C**：仓库状态刷新改为**并发采集 + 逐行增量更新**，两端各自用原生手段实现同一套语义：

1. **并发上限 4**：每端用一个最多 4 并发的工作池采集（Linux：4 个 worker 线程从共享索引抢任务；macOS：`OperationQueue` 的 `maxConcurrentOperationCount = 4`）。
2. **行序稳定**：刷新开始时先按**配置顺序**把行"种"好，结果按 `index` 回填对应行，因此行的顺序与完成先后无关。
3. **种子行**：种行时沿用上一轮同 `path` 的已有数据（新增仓库用空占位），避免刷新瞬间列表闪空。
4. **"采集中"徽标**：尚未出结果的行，状态徽标显示中性的"采集中"（Linux `Checking...` / macOS `Checking…`，灰色），避免把上一轮的旧状态误读成本轮结论。
5. **代际 token**：每轮刷新分配一个自增 token，结果必须带本轮 token 才被接受；被新一轮取代的旧结果直接丢弃（手动刷新与定时刷新叠加时不会互相覆盖）。
6. **收尾语义**：`refreshing`（按钮转圈/禁用）持续到**最后一行**落地才结束；`last_updated` 每落地一行就更新一次。

天气采集不变（本来就是独立任务、独立降级）。

## Rationale

1. 直接消除用户的实际痛点：**首个结果的等待时间**从"全部仓库之和"降到"最快那个仓库"，感知上刷新变成"立刻有反应"。
2. 并发把总耗时降到约 1/4，开 `fetch_remote` 时收益最明显——这部分耗时几乎全是网络等待，天然适合并发。
3. 与"单项失败不拖垮整体"的既有原则一致：现在**慢**也不拖垮整体，一个卡到超时的仓库只影响它自己那一行。
4. 并发上限取 4 而非无上限：worker 阻塞在 git 子进程上，上限同时约束了线程数、并发子进程数和同时对外的 fetch 连接数，行为可预期。
5. 纯 UI 层改动：采集函数（`collect_repo` / `collectRepo`）本来就是"输入一个仓库配置、输出一个 `RepoStatus`"的独立单元，无共享可变状态，天然可并发；§7 规则与全部测试向量不受影响，因此这是一次**不动行为契约**的改动。
6. 两端选同一套语义（同并发度、同种子行策略、同徽标含义），使 UI 观感继续保持一致（ADR-002 靠规格而非代码保证一致）。

## Trade-offs

- UI 多了一个中间态（"采集中"），列表在刷新期间是"部分新、部分旧"的混合状态；靠灰色中性徽标把这件事说清楚，而不是让用户猜。
- 每端多了一点并发状态管理（token / 未完成计数 / 行索引），比原来的"一次性替换整表"复杂。
- 并发 fetch 会在刷新瞬间产生 4 条并发网络请求，对极慢的网络可能比串行更容易触发超时；`command_timeout_secs` 仍是唯一的兜底闸门。
- 采集顺序不再等同于完成顺序，日志/调试时不能再假设"按配置顺序依次执行"。

## Consequences

- **Positive**：刷新体感显著变快（首行秒出、总时长约 1/4）；慢仓库被隔离；`last_updated` 变成"最近一行数据的时间"，新鲜度信息更细。
- **Negative**：两端 UI 层各自多了一份并发/代际逻辑，需要各自维护；这部分逻辑不在测试向量覆盖范围内（它属于有副作用的采集调度层，见 SDD §10.1 的分层）。
- **Mitigation**：把语义写进 SDD §8.1 作为两端共同遵循的契约；代际 token 与行索引回填是防止竞态的关键，两端实现都必须具备（review 时按 §8.1 逐条核对）。

## Revisit Trigger

- 仓库数量级增大（几十→上百），并发度 4 成为新瓶颈，或需要按"本地/远程"区分并发策略。
- 用户反馈"刷新期间列表跳动/新旧混合"难以接受，需要改为"整屏骨架屏"等另一种呈现。
- 未来引入 chezmoi 采集或其他数据源后，需要一个统一的、跨数据源的增量刷新调度层。
