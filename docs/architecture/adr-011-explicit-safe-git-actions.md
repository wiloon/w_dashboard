# ADR-011: 从"纯只读"放开到三个显式的安全同步操作（pull --ff-only / push / fetch）

## Status

Accepted（修订 ADR-001「不做 git 写操作」、SDD §12 非目标的对应条目；不改变 ADR-002 两端独立实现、ADR-003 子进程采集方式、SDD §7.1/§7.2 的解析与派生规则）

## Context

**问题**：面板现在能显示每个仓库的同步状态（`NeedsPull` / `NeedsPush` / `Dirty` / `Diverged` …），
但用户看到 `NeedsPull` 后，仍要**切到终端、cd 进目录、手敲 `git pull`**，再切回面板刷新确认。
"出门前扫一眼、需要就一键同步"是这个面板最自然的下一步——状态已经算出来了，差最后一个动作。

**触发**：作者在使用中直接提出："needs pull 的状态，能不能点一下按钮就执行一次 git pull。"

**原决策（被本 ADR 修订的部分）**：
- ADR-001 / SDD §12：「不做 git 写操作（不代替用户 commit/push/pull）；仅只读展示状态。」
- `.cursor/rules/ui-no-logic.mdc`：「不替用户执行 git/chezmoi 写操作（commit/push/pull/apply）。」

这条约束当初的用意是**避免面板变成一个半吊子 git 客户端**：合并冲突、rebase、交互式提交这些操作一旦做一半，
反而制造麻烦。这个用意依然成立——本 ADR 不推翻它，只是把"绝对不写"收窄为"只做少数几个不可能把仓库搞乱的写操作"。

**约束（不变）**：
- 仍通过子进程调 `git`、复用用户凭据（ADR-003）；不引入 `git2`/`gix`。
- 采集层与 UI 分层不变：操作的线程/异步调度归各端 UI 层（SDD §6/§8）。
- 两端独立实现，一致性靠规格 + `docs/test-vectors/`（ADR-002）。
- 单项失败不拖垮整体（SDD §2）：一个仓库的操作失败只影响它自己那一行。

## Options Considered

| 方案 | Pros | Cons | 复杂度 | 何时合适 |
|------|------|------|--------|----------|
| A. 维持纯只读 | 边界最清晰；零风险；面板永远不会把仓库搞坏 | 用户的核心诉求没满足，每次都要跳终端 | 低 | 面板定位是"纯监视器"，操作一律手动 |
| B. **只做三个显式的安全操作**：`git pull --ff-only`、`git push`、`git fetch`，各配一个按钮，按仓库状态显隐 | 直接满足诉求；`--ff-only` 保证 pull 要么快进要么干净失败，绝不产生合并提交/冲突残留；push 只在"纯领先"时给按钮，天然可推；fetch 完全不碰工作区；失败只落在该行 | 面板从"只读"变成"能写"，需要处理操作进度、结果反馈、操作后重采该行 | 中 | 状态已算好，用户想"看到就一键同步"，但不想要冲突解决那套 |
| C. 完整 git 操作面板（含 merge / rebase / 冲突解决 / commit / stash） | 能力最强 | 正是原约束要避免的"半吊子 git 客户端"；冲突 UI、编辑器集成、部分暂存……复杂度爆炸，且和成熟工具（lazygit / magit / GUI 客户端）重复 | 高 | 目标是做一个 git 客户端——不是本项目的定位 |

## Decision

**选择方案 B**：在 Repos 面板为每个仓库提供最多三个操作按钮，全部是**不可能让仓库进入需要人工善后状态**的安全操作：

| 操作 | 命令 | 何时显示按钮 | 安全性保证 |
|------|------|--------------|------------|
| **Pull** | `git -C <path> pull --ff-only` | `state == NeedsPull`（`behind>0` 且 `ahead==0` 且工作区干净） | `--ff-only`：只能快进，否则**不改动任何东西**直接非零退出；不会产生合并提交，不会进入冲突状态 |
| **Push** | `git -C <path> push` | `state == NeedsPush`（`ahead>0` 且 `behind==0` 且工作区干净） | 仅在本地纯领先时提供；远端若已前进则 push 被拒、干净失败，不改动本地 |
| **Fetch** | `git -C <path> fetch --quiet` | 除 `Error` 外的所有状态，**且 `general.fetch_remote == false`** | 只更新远程跟踪引用，完全不碰工作区与本地分支 |

- `Diverged` 状态**不提供** Pull / Push（需要用户自己决定 rebase 还是 merge），只提供 Fetch。
- `Dirty` 状态不提供 Pull / Push（先让用户处理未提交改动），只提供 Fetch。
- 操作在后台线程/队列执行，执行期间该行按钮禁用并显示进行中文案（`Pulling…` / `Pushing…` / `Fetching…`）。
- 操作结束后，**自动对该仓库重新采集一次**（复用 §7.1/§7.2），使状态徽标反映最新结果；同时在该行显示一行简短结果（成功/失败信息），下次整体刷新时清除。
- 超时沿用 `general.command_timeout_secs`（不新增配置项）。
- **Fetch 按钮仅在 `general.fetch_remote == false` 时显示**：`fetch_remote == true`（默认）时，每次刷新（启动 / 手动 / 定时 / 增删改仓库）已按 §7.1 对每个仓库自动 `git fetch --quiet`，独立的手动 Fetch 按钮是冗余的——"出门前扫一眼"这个场景里，刷新即 fetch。只有用户为省流量 / 避免频繁联网而关掉 `fetch_remote` 时，才需要手动 Fetch 入口。这个条件依赖全局配置而非 `RepoState`，属 UI 渲染规则（SDD §7.5 执行语义 7），不进 `repo-actions/` 向量；Pull / Push 不受影响。

**明确不做**（延续原约束的用意）：`commit` / `merge`（非 ff）/ `rebase` / 冲突解决 / `stash` / `push --force` / 分支切换 / 任何交互式操作。

## Rationale

1. **直接消除用户实际痛点**：面板已经把"要不要同步"判断好了，加一个按钮就省掉"切终端 → cd → pull → 切回来"整个来回。
2. **三个操作都不会把仓库搞成需要人工善后的状态**——这是选它们而不是选方案 C 的关键：
   - `pull --ff-only` 的失败是**无副作用**的（工作区、HEAD 都不动），用户看到失败信息后照旧可以自己去终端处理。
   - `push` 的失败同样不动本地。
   - `fetch` 根本不改工作区。
3. **按状态显隐按钮**，把"这个操作现在是否安全"的判断前置到 UI：`NeedsPull` 一定能 ff（`ahead==0`），`NeedsPush` 一定能 push，不给用户踩坑的机会。
4. **复用既有机制**：命令仍走 ADR-003 的子进程封装、复用用户凭据；操作后重采复用 §7.1/§7.2 与增量刷新的行内回填（SDD §8.1）。
5. **原约束的用意得到保留**：面板没有变成 git 客户端——它只多了"把已经看明白的同步差距一键抹平"的能力，冲突/历史改写这些仍然明确交回给用户和专业工具。

## Trade-offs

- 面板从"只读监视器"变成"能做少量写操作"，边界从"绝不写"变成"只写这三个"——需要靠规格（本 ADR + SDD §7.5）把边界钉死，避免以后一点点滑向方案 C。
- 多了操作进行中 / 操作结果两个 UI 状态，以及"操作后自动重采该行"的调度，两端各自实现、各自维护。
- `push` / `pull` 走网络，可能比 `command_timeout_secs` 更慢；超时后操作可能已在远端部分完成（尤其 push），此时该行重采会显示真实结果，用户据此判断。
- 这三个操作是有副作用、不确定的，**不进测试向量**（与 fetch/采集同属 SDD §10.1 的"采集层"）；只有"给定 RepoState → 允许哪些操作"这个纯函数进向量（`repo-actions/`），作为两端按钮显隐一致性的闸门。

## Consequences

- **Positive**：常见的"需要 pull / 需要 push"两步到一步；面板可用性显著提升；实现上大量复用既有子进程封装与增量刷新。
- **Negative**：两端 UI 层各多一份"操作调度 + 结果展示 + 操作后重采"逻辑；非目标清单需要同步修订（SDD §12 / AGENTS.md / cursor 规则），否则文档与实现相互矛盾。
- **Mitigation**：
  - 把命令、按钮显隐规则、失败降级写进 SDD §7.5，作为两端共同契约。
  - 新增 `docs/test-vectors/repo-actions/`：每个 `RepoState` → `{ pull, push, fetch }` 布尔，两端测试共用。
  - 各端加少量 e2e 冒烟（临时建 bare remote + 本地克隆，制造 behind/ahead，跑 Pull/Push 验证链路）。
  - SDD §12 的非目标条目从"不做 git 写操作"改为精确表述（见该节）。

## Revisit Trigger

- 用户开始要求 `Diverged` 也能一键处理（rebase / merge），或要求 commit / stash——那属于方案 C，需要重新评估"是否要成为 git 客户端"这个定位问题。
- `pull --ff-only` 在实际使用中频繁失败（大量仓库处于 `Diverged`），说明 ff-only 太保守，需要考虑受控的 `--rebase` 选项。
- 操作的网络耗时经常触发超时且造成困惑，需要为写操作单独设置更长的超时或做成可取消。
